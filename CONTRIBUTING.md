# Contributing to procoder

procoder has unusually strong conventions, and CI enforces every one of them.
This page exists so you fail locally instead of in CI.

## Setup

```bash
git clone https://github.com/azrtydxb/procoder
cd procoder
npm install   # no runtime dependencies to fetch — see "Zero runtime dependencies" below
```

## The four checks that gate every PR

| Command | What it checks | Why it fails |
|---|---|---|
| `npm run sync:check` | Generated platform files match the doctrine | You hand-edited a generated file, or edited the doctrine and forgot to regenerate |
| `npm test` | `node --test tests/*.test.js` — 521+ tests, including the self-scan | A behavior regressed, or procoder trips its own rungs |
| `npm run sync` | Regenerates the platform files from the doctrine | Run this, don't run `sync:check` to "fix" things — it only checks |

CI (`.github/workflows/ci.yml`) runs `sync:check` first, then `npm test`, on
Node 20/22/24 across Ubuntu and macOS, with `fail-fast: false` so a red leg
cannot hide the other five. Both must pass locally before you open
a PR — there is no faster feedback loop than running them yourself.

## The doctrine is the single source

`skills/procoder/SKILL.md` is the **only** place the doctrine is authored —
the six rungs, their rules, the thresholds. Everything else that repeats it
is generated by `scripts/sync-rules.js`:

- Nine platform rule files: `AGENTS.md`, `.cursor/rules/procoder.mdc`,
  `.windsurf/rules/procoder.md`, `.clinerules/procoder.md`,
  `.kiro/steering/procoder.md`, `.qoder/rules/procoder.md`,
  `.agents/rules/procoder.md`, `.openclaw/skills/procoder/SKILL.md`, and the
  README's copy of the ladder table (kept in step by hand, the one exception).
- Every `commands/*.toml` ported to `.opencode/command/<name>.md` and
  `.openclaw/commands/<name>.md`.

**If you need to change doctrine text**, edit `skills/procoder/SKILL.md`, then
run `npm run sync` to regenerate everything downstream, then commit both. Hand
editing any of the generated files fails `sync:check` in CI — the check
compares the committed generated files against what `sync-rules.js` would
produce right now, and any drift is a build failure.

## procoder gates itself

`tests/dogfood.test.js` runs `procoder check` over every file `git ls-files`
tracks — including your PR's diff. A change that trips a rung fails the
build. You have three ways out, and only one of them is usually right:

| Way out | When it's right |
|---|---|
| **Fix the code** | The default. Almost always this. |
| `procoder: literal <rule-id> <reason>` marker | The line *describes* a violating pattern rather than committing one — a doctrine paragraph, a detection fixture, a comment quoting a rule id. Trailing on the line, or standalone covering the next line. Must name the rule(s) and give a reason of two-plus words. | <!-- procoder: literal alone/blanket-suppression the marker syntax written out, not a suppression -->
| `.procoderignore` in the directory | An entire directory is generated, vendored, or is a planning document that quotes violations by the hundred — not a case-by-case suppression. |

**Not acceptable**, ever: adding a `.procoder.toml` path exclusion, or a
baseline entry, to make a finding go away. Both widen what the *next* PR gets
away with, silently, which is exactly the rung-4 rot procoder exists to catch.
If you think a finding is a false positive, see the false-positive issue
template — that is the path to fixing the detector, not to hiding the symptom.

## Check ids are permanent

The ratchet baseline (`.procoder-baseline.json`, `hooks/checks/baseline.js`)
fingerprints every accepted finding by its rule id, file path, and normalized
source line. Renaming a check's id — even a typo fix — silently un-suppresses
every finding previously recorded under the old name, because the fingerprint
no longer matches. If a rule genuinely needs a new id, that is a deliberate,
separate change: regenerate the baseline and say so in the PR description.

## Zero runtime dependencies

`package.json` has no `dependencies` field, deliberately — every check, hook,
and CLI command is hand-rolled against Node's standard library. A PR that adds
a runtime dependency needs to argue for it explicitly: what it buys, why the
stdlib or a few lines don't cover it, and what auditing it once bought is worth
across every install of the plugin. Dev-only tooling is a separate
conversation but still needs a reason.

## Tests

Plain `node --test`, no framework, no fixtures library.

- New behavior needs a test that **fails before your change and passes
  after**. This repo has repeatedly caught tests that passed for the wrong
  reason — a stub that never exercised the real path, an assertion that would
  hold even with the bug still in place. Write the test first, watch it fail,
  then make it pass.
- Assert on observable behavior (the finding reported, the exit code, the
  stdout line) — not on internal call order or private state.
- No `sleep()` for synchronization, no dependence on wall-clock time or test
  execution order.

Run everything with `npm test`, or a single file directly:

```bash
node --test tests/shape.test.js
```

## Performance

The PostToolUse hook (`hooks/procoder-check.js`) runs on every file write and
is killed by the harness at **2 seconds** for the whole file
(`BUDGET_MS` in `hooks/checks/run.js`). Several past regressions were
quadratic regex scans on one long line — a minified bundle, a generated file,
a single huge string literal.

If your change adds or touches a regex that scans a line (a new sink pattern,
a new marker, a new language rule), add a timing test proving it stays linear
on a long adversarial line. The existing tests are the template — search
`tests/*.test.js` for `'stays linear on a very long single line'` and
`'stays cheap'` for the pattern to follow: build a multi-hundred-KB line
designed to maximize backtracking for your regex, assert it completes well
under budget.

## Getting help

Open an issue with the relevant template (bug, false positive, or feature —
see `.github/ISSUE_TEMPLATE/`) before a large PR, so the approach gets
discussed before the diff does.
