Using it

Twelve commands

Every command is a Claude Code slash command in the procoder namespace, so they all read /procoder:<verb>. opencode and openclaw get the same twelve, ported from the same source files by scripts/sync-rules.js.

Control the gate

CommandWhat it does
/procoder:levelSet the intensity level: pragmatic, strict, paranoid — or off. Persisted across sessions.
/procoder:guardInstall procoder as a pre-commit hook and a CI check. It detects any hook manager and CI provider you already have and integrates with it rather than over it.
/procoder:statuslineInstall, inspect, or remove the statusline badge. It reports a statusline that is not procoder's rather than replacing it.
/procoder:updateUpdate an installed procoder, and name what the update invalidates — a changed baseline format, or a doctrine change that makes a copied rule file stale.
/procoder:helpThe rungs, the levels and the command list, in one screen.

Hunt for something

CommandWhat it does
/procoder:reviewReview the current diff against the six rungs. Takes an optional commit range or path.
/procoder:auditAudit the whole repository, ranked by rung severity. The deterministic engine runs over the scope before any judgment finding is formed.
/procoder:rotFind dead, stale, and deprecated code left behind — rung 4, run deliberately rather than as a side effect of a diff.
/procoder:threatMap every trust boundary and what validates it: each entry point, what an attacker controls there, and where the validation actually sits.
/procoder:depsAudit dependencies — vulnerable, abandoned, unpinned, unused — by running each ecosystem's own auditor, not a second opinion of its own.

/procoder:rot and /procoder:threat are the two with no equivalent in comparable tools: one hunts what previous changes left behind, the other maps where untrusted data enters and what stops it.

Measure

CommandWhat it does
/procoder:debtA ledger of every procoder: marker in the repository, classified as dated, undated or overdue, flagging any without a removal trigger.
/procoder:gainMeasured progress since a reference point: rot removed, boundaries hardened, baseline shrinkage. Every number comes from git or the baseline file, with the command that produced it.

The commands that report numbers are held to the same standard as this site: /procoder:gain is instructed to derive every figure from git or the baseline file and to show the command behind it, rather than estimating. A progress report that cannot be re-run is a marketing document.

Where they live

Each command is one file under commands/, and most of them invoke a skill of the same name that carries the actual method. The ports to .opencode/command/ and .openclaw/commands/ are generated from those files, and npm run sync:check fails the build if any port has drifted — so there is exactly one place to edit a command, and no copy that can quietly disagree with it.

The CLI

A slash command needs a session; a pre-commit hook and a CI job do not have one. The same engine answers to six subcommands, with no dependencies and no agent behind them.

CommandWhat it does
procoder init [--baseline]Write a starter .procoder.toml. Nothing is overwritten — a config that already exists is left exactly as it is. --baseline also records today's findings as accepted, which is what makes an existing repository green on its first run rather than red by four thousand.
procoder check [paths...]Report findings that are not in the baseline; exit 1 if any of them blocks at the active level.
procoder baseline <paths...>Record every current finding as accepted, so only new code is gated.
procoder verify <paths...>Exit 1 if a finding present today is not in the baseline — the CI ratchet. Exit 2 is cannot verify, never "you added findings".
procoder rot <paths...>Rung 4 over the tree: index every export in the scan and report the ones nothing else mentions, as [4 ALONE] alone/dead-export.
procoder deep <paths...>Taint analysis with CodeQL over the whole tree, at --threat-model=all. This is the tier that catches injection, path traversal and log forging — the classes where the code is idiomatic and only the data's provenance makes it wrong, which no pattern matcher can see. Takes minutes and builds a database, so it belongs in a pre-commit hook or CI, never on a write. Compiled languages need [codeql] build_command in .procoder.toml; a language it cannot analyse is named, never skipped silently.
procoder doctorReport which mandated analyzers are installed, their versions, and how to update them. Exits 1 if any is missing or incomplete — procoder carries no rules of its own, so a missing analyzer is a hole in the gate rather than a preference, and files in its languages are reported as ungated rather than clean.
procoder statusline <install|uninstall|status>Wire procoder's level badge into Claude Code's statusLine, or take it out again. --append keeps a statusLine you already have and prints the badge after it; --force replaces one that is not procoder's.

Who reads the output: check --format

text is the default and is for a person. json is procoder's own versioned shape — version, tool, level, summary, findings[], skipped[] — so a consumer can tell an old document from a new one. sarif is SARIF 2.1.0, for GitHub code scanning and anything else that speaks it, and it carries partialFingerprints.procoderFingerprint: the same fingerprint the ratchet uses, so a finding that moved down the file is not a fresh alert to triage again.

Findings go to stdout and every skip notice stays on stderr, so the document stays parseable when you pipe it. Both formats also name the files the run skipped: JSON in a skipped array, SARIF as invocations[0].toolExecutionNotifications, with executionSuccessful false when a file that was in scope could not be read at all. A file nobody opened cannot arrive at a dashboard looking like a file that was scanned and found clean. --format belongs to check; typed at any other subcommand it exits 2 rather than being quietly ignored.

What gets checked: check --since <ref>

Checks what git says changed — git diff --name-only --diff-filter=ACMRT <ref>...HEAD, plus anything uncommitted and anything untracked. Renames, copies and type changes are included at their new path; deletions are not, having no bytes left to scan. Paths given alongside narrow it to the intersection, so --since main src/ means "what changed under src/".

--since is not "check only": --aging and --unused-exclusions are honoured rather than dropped, judged over what this run read. The baseline is what --aging asks about and no file selection narrows that, so it behaves exactly as it does on a whole-tree run. --unused-exclusions makes only the claims a partial scope can support — "this glob matches nothing" needs to have seen the tree, so under --since it stays unmade.

A git failure exits 2 and names the command that failed. The shipped CI template used to do this in shell with || true, where a first push (whose "before" SHA is all zeros) made git fail, produced no files, and passed the build green having checked nothing. Zero changed files is a real answer and is said out loud — no files changed since <ref>, exit 0 — because silence and a clean scan of a hundred files must not look the same.

Debt with an end: verify --aging <days>

Names every accepted finding that has been in the baseline longer than <days>, with its date, path and rule, and exits 1. A baseline entry is a suppression, and a suppression with no end is rot; this is the removal trigger the file itself cannot carry. Without the flag, age never fails a run.

How many cores: --jobs <n>

A scan splits its file list into contiguous slices and hands each to a worker process. The default is one per usable core — os.availableParallelism(), which sees a container's CPU quota where os.cpus() reports the host's cores through it — capped at 8, and 1 — this process, no workers — for a run whose measured sequential cost is under 900 ms, where forking costs more than it saves. The cost is measured, not guessed: a strided sample of the run's own files is scanned for real and the rest extrapolated from it, so a subprocess linter, a cold disk or a slow host is seen. The report is identical either way: slices are reassembled in input order, every file runs at the same 2,000 ms budget whichever process reads it, and a worker that dies, or hangs past a derived slice bound, has its slice rescanned here rather than dropped. --jobs 1 takes the pool out of the picture entirely.

The value is clamped. Anything from 1 to 8 is honoured silently; above the ceiling it is refused with a warning naming the value and the ceiling; and zero, a negative, a non-number or an empty value is refused the same way and the default is used. Coercing a typo in a CI invocation into the default in silence made it look exactly like not passing the flag at all.

Why is this not checked: --no-ignore

Checks files a .procoderignore covers anyway. It reaches ignore files and nothing else — [exclude] paths in .procoder.toml is the project-wide contract and carries the built-in node_modules/ defaults, so a flag that reached it would be a back door rather than a diagnostic. Every file that key holds back is reported by count per pattern, or by name if you named that file yourself.

Suppressions that stopped earning it: verify --unused-exclusions

Also fails the build when an [exclude] rules entry suppressed nothing this run, or an [exclude] paths entry or a .procoderignore pattern holds nothing back — its path is gone, it matches no file, or every file it covers is clean. All three are reported under plain verify and fail only under the flag, and the tree-wide judgments are made only when the run covered the whole repository.

What nothing calls: rot

Two tiers, and the difference is the whole honesty of the command. A name nothing else in the scan mentions is a deletion. A name mentioned outside its own file only inside a string is needs confirmation: routing tables, DI containers and reflection all look exactly like that, and an index of bare words cannot tell them apart.

Files a published package points at — bin, main, module, exports in package.json — and conventional entry points (index.*, lib.rs, mod.rs, __init__.py) are left out, because their callers are outside the scan and reporting one as dead is the failure that would make the whole report untrustworthy. Test fixtures and example files are exported-and-unmentioned by design and will appear: exclude them under [exclude] paths, or read past them.

It exits 0 even with findings. These are candidates, not verdicts, and nothing is ever deleted — a build failed on a guess about deletion is how a tool gets switched off, and rightly.
