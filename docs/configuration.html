Using it

Configuration

Four mechanisms, in descending order of how much they narrow the gate: .procoder.toml configures the engine project-wide, .procoderignore excludes paths, the literal marker excuses one line, and the baseline accepts today's debt without accepting tomorrow's. Every one of them is visible in the diff, on purpose.

.procoder.toml

Sits at the repository root and configures rung severities, shape thresholds and exclusions. Every key is optional; the values below for [thresholds] and [baseline] are the defaults. 

[rungs]
safe = "error"
true = "error"
obvious = "warn"
alone = "warn"

[thresholds]
function_lines = 40
nesting_depth = 3
params = 4
complexity = 10

[exclude]
paths = ["vendor/", "generated/"]
rules = ["scripts/legacy-parser.js:obvious/complexity"]

[baseline]
file = ".procoder-baseline.json"

[rungs] sets each rung's severity. error findings are reported as must-fix, warn findings as advisory, and the active level modulates that: at pragmatic the judgment rungs are flagged without blocking language, while SAFE and TRUE always demand a fix. The keys are the four rung names verbatim, true included — it is a bare key, not a boolean.

[exclude] paths takes directory prefixes and excludes them from every check. [exclude] rules is the narrow form: each entry is path:rule-id, and the path must match a file exactly — no directory prefixes, no globs. Because the match is exact rather than a prefix, a rule-scoped exclusion cannot silently widen to cover files added later under the same directory. Narrowing enforcement always takes a second, deliberate edit.

The TOML parser is a documented subset, not a full implementation. A line it cannot recognise is warned on stderr and skipped, never silently dropped — but an unsupported value on a well-formed line is not warned, and loads as raw text. Keep this file to the shapes above, and read stderr after editing it. The exact boundaries are in known limitations.

.procoderignore

A .procoderignore may sit in any directory and excludes paths in that directory and everything beneath it — so a large generated subtree is excluded by one file next to it, rather than by a central list that grows stale far from what it describes. 

*.gen.ts        # any depth below this directory
/vendor/        # only this directory's vendor/, not a nested one
build/          # a directory of that name, at any depth
!keep.gen.ts    # ...except this one

The syntax is a subset of .gitignore, and this list is exhaustive — anything not on it is not supported:

SupportedMeaning
comments, blank linesSkipped. Leading and trailing whitespace is trimmed.
nameMatches name — and everything under it if it is a directory — at any depth below the ignore file.
a/b.tsA slash anywhere anchors the pattern to the ignore file's own directory.
/vendorA leading slash anchors it too.
build/A trailing slash matches only a directory's contents, never a file of that name.
*Any run of characters within one path segment.
**Any run of characters across segments; **/ also matches zero directories.
!patternNegation — puts a path back into the gate.

Not supported, and treated as literal characters rather than silently doing something else: ?, character classes, and backslash escapes. A line that cannot be compiled is dropped and matches nothing; an ignore file that cannot be read, or is full of nonsense, ignores nothing and never fails a hook.

Precedence, in order:

  1. .procoder.toml's [exclude] paths is decided first and its verdict is final. A negation in a .procoderignore cannot re-include what the root config excluded — a subdirectory may narrow further, never contradict.
  2. Otherwise the last matching pattern wins, and a deeper ignore file's patterns are applied after a shallower one's, so the deepest file decides — as in git.
  3. Only ignore files in a path's own ancestor directories are read, so an ignore file cannot reach above its own directory. A pattern naming a parent is dropped.

.gitignore is deliberately not read. A file being untracked says something about version control, not about whether it should ship — and the in-session hook fires on files git has never seen. Inheriting those patterns would narrow the gate by reusing a file written for another purpose, silently. Ignoring a path from procoder takes a line in a file whose name says so.

Because an ignore file narrows enforcement, every run reports one line on stderr per ignore file that actually skipped something — per ignore file, not per file, so the notice cannot bury the findings it was meant to make room for. To check an ignored file anyway, pass --no-ignore, which turns off every .procoderignore for that run and nothing else.

The literal marker

The narrowest form of all, and the only one not written in a config file. It is for text that describes a violation rather than committing one: a detection pattern, a doctrine paragraph, a fixture, a rule id quoted in config. This page uses one. 

<comment syntax> procoder: literal <rule-id>[, <rule-id>…] <reason>
RuleWhy
It must name its rules, comma-separated. There is no bare form and no wildcard. An unnamed suppression is a rung-4 violation by this project's own doctrine, and is reported as one.
It must state a reason of at least two words. A marker with no reason does not parse, silences nothing, and is itself reported.
The reason runs to end of line, so the marker is always last on its line. That is what separates a trailing marker (this line only) from a standalone one (its own line and the next) — the widest scope offered. There is no block or file form.

It can name any built-in rule, including the credential rule — a mechanism that could not cover a credential could not cover the fixtures and doctrine pages where the false positives actually are. What keeps it honest is that it names the rule, states a reason, reaches at most two lines, and sits in the diff right next to the value. A rule id it does not recognise is dropped from the marker rather than silently honoured: the finding still reports and the unknown id is named on stderr, so a typo fails loudly instead of quietly widening what the marker covers.

The ratchet baseline

procoder baseline <paths...> records every current finding as accepted; procoder verify <paths...> fails when a finding appears that is not in that record. Accepted debt may shrink, never grow.

Findings are fingerprinted from the rule id, the file path, the normalised text of the line, and an occurrence ordinal — deliberately not the line number. So reindenting a file or moving a suppressed line does not resurrect a suppressed finding, and copy-pasting a suppressed line does not ride in for free. A re-wrapping formatter, or code moved between files, does break the fingerprint; what it misses covers exactly which cases.

verify --unused-exclusions additionally fails when an [exclude] rules entry suppressed nothing in the run — a stale suppression left behind after the finding it silenced was fixed is itself rung-4 rot. Without the flag those entries are still reported, they just do not fail the build.

Environment variables

VariableEffect
PROCODER_DEFAULT_LEVELOverrides the default level (strict) for new sessions. One of off, pragmatic, strict, paranoid.
PROCODER_NO_HOOKSet to 1 to disable all procoder hooks — activation, level tracking, subagent propagation — without uninstalling the plugin.
CLAUDE_CONFIG_DIRWhere procoder persists the active level, as <dir>/.procoder-active. Defaults to ~/.claude.
PROCODER_HOSTSelects the hook wire protocol for non-Claude-Code hosts: codex, copilot, or qoder. codex is also auto-detected via CODEX_HOME.
PROCODER_NO_UPDATE_CHECKSet to 1 to turn off the update notice, including its once-a-day background request. Nothing else changes.
PROCODER_UPDATE_URLWhere the update check reads the published version from. Point it at a fork or an internal mirror if you install from one.

The update check is a single unauthenticated GET of a static file, at most once a day, sending nothing about you or your code. Session start never waits on the network: the hook reads a cached answer and refreshes in a detached process for the next session, so the first session after a release is silent by design and the one after it notifies.
