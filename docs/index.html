Claude Code plugin · v0.2.0

procoder

An AI writes the change in seconds. What it rarely does is delete the thing the change replaced — so the old path survives, still exported, still called, still wrong. procoder is the gate that refuses to call that done.

  • Zero runtime dependencies
  • MIT
  • Node ≥ 18

procoder is a Claude Code plugin that governs whether AI-written code is allowed to ship. Every response is checked against four rungs, in order, and a deterministic check engine runs over each file the session touches. It pairs with the ponytail plugin: ponytail decides what to write (the minimal solution), procoder decides whether it may ship.

This is v0.2.0. The check engine is a set of heuristics, not a parser — it will miss things, and the ones it is known to miss are written down in Known limitations. Read that page before you rely on this to keep anything out.

The four rungs

ponytail's ladder is stop at the first rung that holds — a search. procoder's ladder is every rung must hold before it ships — a gate. Checked in this order because the cost of getting it wrong descends.

#RungQuestionNegotiable
1SAFEDoes untrusted data reach a sink unvalidated?No
2TRUEAre errors handled and edges covered, with one runnable check left behind?No
3OBVIOUSWould the next reader get it in one pass?Judgment
4ALONEDid you leave a twin behind?Judgment

Rung 4 is the rung nobody ships, and the reason procoder exists: a change isn't done until the thing it replaced is gone.

Levels

LevelEnforces
offprocoder is disabled entirely.
pragmaticSAFE and TRUE enforced; OBVIOUS and ALONE flagged only, non-blocking.
strict (default)All four rungs enforced on code touched this session.
paranoidstrict, plus a threat-model note on every new trust boundary, and ALONE applied to whole files rather than just the diff.

Switch mid-session with /procoder:level <level>. The choice is persisted, so it outlives the session and survives restarts.

Install

In Claude Code:

claude plugin marketplace add azrtydxb/procoder
claude plugin install procoder

Installing from a clone instead? Point the marketplace at the path: claude plugin marketplace add ./procoder.

To see the active level in your status line:

procoder statusline install

For a pre-commit hook, a CI job, or a plain terminal with no agent in it:

npm install -g procoder

procoder check <paths...>     # exit 1 if a non-baselined finding blocks
procoder baseline <paths...>  # record current findings as accepted
procoder verify <paths...>    # exit 1 if a finding isn't in the baseline

Cursor, Windsurf, Cline, Kiro, Qoder, opencode, openclaw, Codex/Copilot, pi and MCP each read a rule file generated from the same doctrine source. The exact commands per host are in docs/install.md.

Commands

CommandPurpose
/procoder:levelSet the intensity level: pragmatic, strict, or paranoid.
/procoder:reviewReview the current diff against the four rungs.
/procoder:auditAudit the whole repository, ranked by rung severity.
/procoder:rotFind dead, stale, and superseded code left behind.
/procoder:threatMap every trust boundary and what validates it.
/procoder:depsAudit dependencies: vulnerable, abandoned, unpinned, unused.
/procoder:debtLedger of procoder: markers, flagging any without a removal trigger.
/procoder:gainMeasured progress: rot removed, boundaries hardened, baseline shrinkage.
/procoder:guardInstall procoder as a pre-commit hook and CI check.
/procoder:statuslineInstall, inspect, or remove the statusline badge.
/procoder:updateUpdate procoder, and name what the update invalidates.
/procoder:helpShow procoder's rungs, levels, and commands.

/procoder:rot and /procoder:threat have no equivalent in comparable tools: one hunts what previous changes left behind, the other maps where untrusted data enters and what validates it.

A worked example

The repository carries one before/after pair per rung under examples/. They are not illustrations: tests/examples.test.js asserts that every before.ts trips its rung and every after.ts reports nothing, so a pair that stopped teaching would fail the build. Here is the SAFE pair, quoted from the real files.

examples/safe/before.ts

export async function updateUserRole(
  req: Request, res: Response,
): Promise<void> {
  const { userId, role } = req.body;

  // trusts the caller's own claim of
  // admin-ness instead of looking it
  // up server-side
  if (req.body.role === 'admin') {
    await db.query(
      `UPDATE users SET role = '${role}'
       WHERE id = '${userId}'`);
  }

  res.sendStatus(204);
}

examples/safe/after.ts

export async function updateUserRole(
  req: Request, res: Response,
): Promise<void> {
  const { targetId, role } =
    parseRoleChange(req.body);
  const actingRole =
    await currentUserRole(req.auth.userId);

  if (actingRole !== 'admin') {
    res.sendStatus(403);
    return;
  }

  await db.query(
    'UPDATE users SET role = $1 WHERE id = $2',
    [role, targetId]);
  res.sendStatus(204);
}

What the engine says about each, verbatim:

$ node bin/procoder.js check --no-ignore examples/safe/before.ts
[1 SAFE]    examples/safe/before.ts:14 SQL built by interpolation or
            concatenation → use a parameterized query with bound values

procoder: 1 finding. Fix them, or run `procoder baseline <paths>` to
accept pre-existing ones.

$ node bin/procoder.js check examples/safe/after.ts
$ echo $?
0

Note what the engine did not report: the authorization decision made from req.body.role. No regex can tell a role read from a request body apart from any other property read. That half of the example is caught by the doctrine the agent reads — rung 1, "validate at the boundary, not downstream" — not by the deterministic check. The engine and the doctrine cover different ground, and the engine covers the smaller half.

The other three pairs, and what each reports today:

PairReported on before.ts
true/ an error swallowed by an empty catch (1 finding). The unhandled empty-array edge in the same file is doctrine, not a rule.
obvious/ nesting depth 4 over a limit of 3; a 56-line function over 40; 6 parameters over 4; cyclomatic complexity ~15 over 10; a nested ternary (5 findings).
alone/ two deprecation marks with no removal trigger, and 3 lines of commented-out code (3 findings).

Run any of them yourself from a clone:

node bin/procoder.js check --no-ignore examples/obvious/before.ts
node bin/procoder.js check examples/obvious/after.ts

Configuration

.procoder.toml

Configures the check engine: rung severities, thresholds, exclusions.

[rungs]
safe = "error"
true = "error"
obvious = "warn"
alone = "warn"

[thresholds]
function_lines = 40
nesting_depth = 3
params = 4
complexity = 10

[exclude]
paths = ["vendor/", "generated/"]
rules = ["scripts/legacy-parser.js:obvious/complexity"]

[baseline]
file = ".procoder-baseline.json"

The [thresholds] and [baseline] values shown are the defaults; every key is optional. The [rungs] keys are the four rung names verbatim, true included — it is a bare key, not a boolean. [exclude] rules is exact-path-only: no directory prefixes, no globs, so a rule exclusion cannot silently widen to files added later. A line the parser cannot recognize is warned on stderr and skipped, never silently dropped — and the parser is a documented subset of TOML, worth knowing before you write anything exotic in there.

.procoderignore

A .procoderignore may sit in any directory and excludes paths in that directory and everything beneath it, using a documented subset of .gitignore syntax — *, **, anchoring slashes, trailing-slash directories, and ! negation. ?, character classes and backslash escapes are not supported and are treated as literal characters. 

# gen/.procoderignore
*.gen.ts        # any depth below gen/
/vendor/        # only gen/vendor/, not gen/pkg/vendor/
build/          # a directory of that name, at any depth
!keep.gen.ts    # ...except this one

.gitignore is deliberately not read: a file being untracked says something about version control, not about whether it should ship. Every run reports one line on stderr per ignore file that actually skipped something, so a narrowed gate is visible rather than silent. To check an ignored file anyway, pass --no-ignore.

The literal marker

For text that describes a violation rather than committing one — a detection pattern, a doctrine paragraph, a test fixture, a rule id quoted in config — the suppression is written on the line itself: 

<comment syntax> procoder: literal <rule-id>[, <rule-id>…] <reason>

It must name its rules (there is no bare form and no wildcard), and state a reason of at least two words — a marker that does neither silences nothing and is itself reported. Trailing on a line it covers that line; standing on its own line it covers that line and the next. There is no block or file form. An unrecognised rule id is dropped from the marker and named on stderr, so a typo fails loudly instead of quietly widening what it covers.

Environment variables

VariableEffect
PROCODER_DEFAULT_LEVELOverrides the default level (strict) for new sessions.
PROCODER_NO_HOOK1 disables all procoder hooks without uninstalling the plugin.
CLAUDE_CONFIG_DIRWhere the active level is persisted (<dir>/.procoder-active). Defaults to ~/.claude.
PROCODER_HOSTHook wire protocol for non-Claude-Code hosts: codex, copilot, qoder.
PROCODER_NO_UPDATE_CHECK1 turns off the update notice and its once-a-day background request.
PROCODER_UPDATE_URLWhere the update check reads the published version from. Point it at a fork or mirror.

The update check is a single unauthenticated GET of a static file on raw.githubusercontent.com, at most once a day, sending nothing about you or your code. Session start never waits on it: the hook reads a cached answer and refreshes in the background for the next session, so the first session after a release is silent by design.

What it misses

procoder gates other people's code. That obligates candour about where the gate is weak, so the blind spots are written down and kept current rather than left for you to discover: docs/known-limitations.md. The short version:

  • It scans heuristically, it does not parse. The shape checks are a brace and indent counter over six languages. A JS/TS private class member (#count) blanks the rest of its own line, so a private method can escape the length, parameter and complexity rules entirely.
  • Long things fall out of range. Regex spans stop at 500 characters (200 in the universal pack), a wrapped signature is given up on after 10 lines, shape rules skip any line over 4KB, and files over 4MB are not checked at all.
  • The ratchet baseline is fingerprint-based. It survives reindentation and line moves, but a re-wrapping formatter, or code moved between files, resurrects accepted findings as new ones.
  • The line marker cannot name an external linter's rule id (true/eslint:no-eval) — the marker still parses, and silences nothing. Use [exclude] rules for those.
  • cargo clippy cannot be scoped to one file, so on any non-trivial crate it usually exceeds its timeout and the built-in Rust pack covers the file instead.
  • The in-session hook only reports near the edit (±3 lines) for language-pack findings. Run procoder check <file> or /procoder:review for the whole-file picture.

It is held to its own gate

tests/dogfood.test.js runs procoder check over every file git ls-files reports, so a file is in the gate the day it lands, and it plants a violation in a temp directory each run to prove the scan still fails on one. A tool that exempted itself from its own doctrine would have already lost the argument. The suite is 521 tests (npm test, Node's built-in runner, no test framework) — that counts assertions of the engine, hooks, CLI, config parsers and the self-scan, not lines of the tool covered.
