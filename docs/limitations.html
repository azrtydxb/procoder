Honesty

What it misses

procoder gates other people's code. That obligates candour about where the gate is weak — so here are the findings procoder would file against itself, in the format it files everything else, against real paths in this repository.

  • [6 MEANT] hooks/checks/finding.js rungs 5 and 6 have no engine behind them at all → no fast/ or meant/ rule id exists anywhere in hooks/, so [rungs] fast = "error" is inert and CI can never gate on cost or on scope creep
  • [2 TRUE] hooks/checks/report.js SARIF carries no record of the files a run skipped → runs[0] holds tool and results and nothing else, so a file that was too large to read is indistinguishable in the document from a file that was scanned and found clean
  • [2 TRUE] bin/procoder.js --since does not see a rename → --diff-filter=ACM excludes R, so a commit that renames a file prints no files changed — nothing to check and exits 0 over a live safe/sql-injection
  • [2 TRUE] hooks/checks/worker.js the time budget is not the same in a worker as in this process → 600,000 ms against 2,000 ms, so the deadline that appends true/budget-exhausted fires on a sequential scan and effectively never on a parallel one
  • [1 SAFE] hooks/checks/lang/taint.js a wrapping call at a binding cannot be told from an escaper → q = sanitizeSql(q); before the sink still reports, in all six packs, and so does the driver's own mysql.escape(id)
  • [1 SAFE] hooks/checks/lang/taint.js the database gate asks about the file, not the call → in a module that also runs SQL, redis.execute(cmd) or runner.execute(step) on a built string reports safe/sql-injection
  • [1 SAFE] hooks/checks/lang/taint.js and the reverse of that gate → const q = base + req.query.id; then api.execute(q); in a file holding no database vocabulary reports nothing at all
  • [1 SAFE] hooks/checks/lang/taint.js a parameter arriving already tainted is deliberately not followed → function f(q) { db.query(q); } is silent, because nothing in the file separates the untrusted caller from the constant one
  • [1 SAFE] hooks/checks/lang/ts.js safe/xss-sink fires on the assignment target, not the value → const safe = escapeHtml(x); el.innerHTML = safe; is reported, and it is correct code
  • [1 SAFE] hooks/checks/universal.js safe/redaction-marker cannot tell prose from code → a Markdown sentence describing the mechanism reports one, and the pattern is case-sensitive, so a lower-case marker in a real file does not
  • [1 SAFE] hooks/checks/deps.js safe/manifest-not-locked is npm-only and text-matched → a peerDependencies entry reports although it is the consumer's to install, and a direct dependency the lockfile knows only as somebody else's transitive does not
  • [2 TRUE] hooks/checks/lang/py.js true/missing-timeout reads the call as text → requests.get(url, **DEFAULTS) reports even when DEFAULTS carries the timeout, and httpx, urllib, aiohttp, fetch and Java's HttpClient are not checked at all
  • [3 OBVIOUS] hooks/checks/shape.js a parameter list on a very long line has no ceiling → a 1,000-parameter single-line signature is measured and reported, because obvious/too-many-params is not span-derived and the 4 KB line guard does not cover it
  • [4 ALONE] bin/procoder.js nothing ever prunes the baseline → procoder baseline only appends, so an entry whose finding was fixed stays forever and verify --aging then fails CI naming files that no longer contain it
  • [3 OBVIOUS] hooks/procoder-check.js in-session findings are narrowed to the edited region and truncated to five → run procoder check on the file for the whole-file picture; the MCP server's procoder_check truncates the same way and says so even less

None of those are hypothetical, and none of them are the whole list. Each was produced by running the tool on a throwaway file at 0.2.0.

Those fifteen lines are a pointer, not a second copy: every one of them is restated from docs/known-limitations.md, which is the only place a limitation is recorded, measured and dated. This page is a twin by rung 4's definition. Five audits running it drifted the same way — into claiming a defect the engine had already stopped having. This one drifted the other way, and worse: the engine grew a parallel scanner, two machine-readable formats, a --since, an init, two rungs and three rules, and this page said nothing about any of it. Silence about new surface is the same dishonesty in different clothes. What went from this page in this pass: the JS method shorthand named after a statement and Rust's fn r#match, both now measured; the template literal holding a quote, which no longer desynchronises the brace scan; and .procoderignore having no expiry test, which it now has. What arrived is everything above the taint rows. If the two ever disagree, the markdown is right and this page is stale.

The engine covers the smaller half

The most important limitation is structural rather than a bug. procoder is two things, and only one of them is deterministic.

Where a finding can come from

The check engine is regex and counters over six languages. It runs after every file write and from the CLI, it is reproducible, and it is what CI gates on. It catches an interpolated query, a swallowed error, an over-long function, an unexplained suppression — 44 rule ids, all of them at rungs 1 to 4.

The doctrine is text the agent reads. It catches the things no regex can: an authorization decision made from a value the caller supplied, a missing edge case, a name that lies, a replaced path nobody deleted. It is not reproducible, and it is not a gate CI can run.

For rungs 5 and 6 the overlap is empty. FAST and MEANT are doctrine and nothing else: no check in the engine can produce a finding at either, so a query per row over a request-sized list and a rename nobody asked for both pass procoder check in silence. A worked instance of the split — the same file, one half caught by the engine and the other only by the doctrine — is on the six rungs.

What the self-scan proves, and what it does not

tests/dogfood.test.js derives its file list from git ls-files, so every tracked file is in the gate the day it lands, this page and its stylesheet included. Running the tool over this repository today, node bin/procoder.js check . reports 0 findings over 209 tracked files and exits 0, having skipped 18 of them and said so on stderr for every one: 9 by [exclude] paths in .procoder.toml, one line per pattern with its count, and 9 across two .procoderignore files. So 191 files are actually read — the number the README publishes, and the one tests/dogfood.test.js asserts against the scan's own output so it cannot drift.

It is also, at 209 files, below the 250-file threshold at which the scan forks workers — so procoder's own self-scan never exercises the parallel path.

What that does not prove: the scan is only as strong as the engine, and the engine is the smaller half. A clean self-scan means procoder finds nothing wrong with procoder — which is exactly the claim a heuristic tool is worst placed to make about itself. It is evidence that the tool is not exempting itself, not evidence that the code is correct.

Those 9 are held out by a .procoderignore sitting next to what it describes: 5 historical planning documents that quote rule ids by the hundred, and the 4 examples/*/before.* files that violate a rung on purpose. The latter are still proved on every run, through procoder check --no-ignore. Every ignore pattern is now judged for expiry on a whole-tree verify — reported when every tracked file it covers scans clean with that one line lifted, or when a glob matches nothing — with two gaps kept on purpose: there is no "the path is gone" rule, because a literal path is a fence around a location that a fresh clone legitimately lacks, and a negated pattern is never judged, because "this exception stopped mattering" is not coverage lost. Where git ls-files cannot answer, nothing is judged at all.

The 9 held by [exclude] paths are the 7 tests/fixtures/*/dirty.* files — inputs whose whole purpose is to be scanned by the tests rather than by the scan, where a line marker would change the input the test reads — plus .opencode/command/rot.md and .openclaw/commands/rot.md, which carry one named finding each. That key was 46 files until recently, on the argument that scripts/sync-rules.js generates 32 of them from the doctrine. The argument was sound and the scope was not: 30 of the 32 held back no finding at all, because they are rendered from a source file that is itself in the gate, so they are gated now too. The remaining two are the one false positive, not a category.

That key used to be the quietest hold-out procoder offered. It is not now: every run prints one stderr line per pattern with its count and the pattern that did it, naming a file directly if you named that file yourself, and all three instruments — rule exclusions, path exclusions, ignore patterns — are re-judged on every verify and fail the build under --unused-exclusions. None of that reaches --format json or sarif: --format is refused off check and the staleness report is verify output, so a dashboard-only pipeline has to run a second, text-mode verify to learn that a directory has been quietly un-gated.

--no-ignore deliberately does not reach [exclude] paths: the flag turns off ignore files and stops there, because the root config is the project-wide contract and carries the built-in node_modules/ defaults. A flag that reached it would be a back door, not a diagnostic — and the counts above answer the question the flag exists to ask.

The full list

docs/known-limitations.md is the authoritative document. Every entry in it was verified against the source cited next to it, or by running the tool, and it carries its own note saying when that verification was done. Entries that were fixed are deleted rather than kept as false modesty — a document that overstates weakness is as untrustworthy as one that hides it.
