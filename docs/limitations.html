Honesty

What it misses

procoder gates other people's code. That obligates candour about where the gate is weak — so here are the findings procoder would file against itself, in the format it files everything else, against real paths in this repository.

  • [1 SAFE] hooks/checks/lang/ every rung-1 rule reads one line, inside the sink → bind the query to a variable first and nothing is reported
  • [2 TRUE] hooks/checks/resolve.js clippy writes to stderr, the runner reads stdout → a Rust crate with clippy configured gets fewer findings than one without
  • [3 OBVIOUS] hooks/checks/lang/py.js depth is columns divided by a hard-coded tab width of 4 → Python indented two spaces per level reports half its real nesting
  • [4 ALONE] hooks/checks/baseline.js fingerprint keys on the finding's own line text → re-baseline after a formatter sweep, or accepted findings return as new
  • [3 OBVIOUS] hooks/procoder-check.js in-session findings are narrowed to the edited region → run procoder check on the file for the whole-file picture

None of those are hypothetical, and none of them are the whole list.

Those five lines are a pointer, not a second copy: every one of them is restated from docs/known-limitations.md, which is the only place a limitation is recorded, measured and dated. This page is a twin by rung 4's definition and has drifted from that document before — twice, both times into claiming a defect that had already been fixed. If the two disagree, the markdown is right and this page is stale.

The engine covers the smaller half

The most important limitation is structural rather than a bug. procoder is two things, and only one of them is deterministic.

Where a finding can come from

The check engine is regex and counters over six languages. It runs after every file write and from the CLI, it is reproducible, and it is what CI gates on. It catches an interpolated query, a swallowed error, an over-long function, an unexplained suppression.

The doctrine is text the agent reads. It catches the things no regex can: an authorization decision made from a value the caller supplied, a missing edge case, a name that lies, a replaced path nobody deleted. It is not reproducible, and it is not a gate CI can run.

A worked instance of that split — the same file, one half caught by the engine and the other only by the doctrine — is on the four rungs.

What the self-scan proves, and what it does not

tests/dogfood.test.js derives its file list from git ls-files, so every tracked file is in the gate the day it lands, this page and its stylesheet included. Running the tool over this repository today, node bin/procoder.js check . reports no findings and exits 0.

What that does not prove: the scan is only as strong as the engine, and the engine is the smaller half. A clean self-scan means procoder finds nothing wrong with procoder — which is exactly the claim a heuristic tool is worst placed to make about itself. It is evidence that the tool is not exempting itself, not evidence that the code is correct.

Some paths are held out by a .procoderignore sitting next to what it describes: historical planning documents that quote rule ids by the hundred, and the examples/*/before.* files that violate a rung on purpose. The latter are still proved on every run, through procoder check --no-ignore. No ignore file has an expiry test, so one covering a path that has since gone clean would not be reported — the per-run stderr line naming each ignore file and its count is what keeps that visible.

The full list

docs/known-limitations.md is the authoritative document. Every entry in it was verified against the source cited next to it, or by running the tool, and it carries its own note saying when that verification was done. Entries that were fixed are deleted rather than kept as false modesty — a document that overstates weakness is as untrustworthy as one that hides it.
