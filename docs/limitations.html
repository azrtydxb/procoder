Honesty

What it misses

procoder gates other people's code. That obligates candour about where the gate is weak — so here are the findings procoder would file against itself, in the format it files everything else, against real paths in this repository.

A decision we made deliberately is not a limitation. This page carries two kinds of entry and no longer carries a third. A genuine gap is something the tool cannot do. An accepted trade-off is something it chose not to do, which still costs you a finding — those say what they buy as well as what they cost. Everything that is simply the reason the tool is shaped the way it is — the ratchet's fingerprint, the TOML subset, the file-size ceilings, the self-scan's own 18 skips — moved to Why it works this way, where it reads as design rather than apology.

  • [6 MEANT] hooks/checks/judgment.js rungs 5 and 6 have three rules between them, out of 47 → almost all of MEANT stays doctrine-only, because scope creep is a relationship between a change and a request and a line scanner has never seen the request
  • [1 SAFE] hooks/checks/lang/taint.js an escaper is trusted by name, not by what it escapes for → db.query(escapeHtml("SELECT * FROM t WHERE id=" + id)); reports nothing, and neither does sanitizeNothingAtAll(q) before the sink. Accepted: it buys four rung-1 false positives on correct escaping
  • [1 SAFE] hooks/checks/lang/taint.js escaping the assembled query passes as a fix → q = "SELECT id=" + id; then q = sanitizeSql(q); then db.query(q); is silent, and the injection was already in the string
  • [1 SAFE] hooks/checks/lang/taint.js a receiver name decides whether a call is a database call → a real pg pool bound to cache, api or queue is never a SQL sink, whatever the file holds
  • [1 SAFE] hooks/checks/lang/taint.js a project-local sanitiser is still a false positive → q = clean(q); and q = harden(q); before the sink both report, kept on purpose: a wrapping call clearing taint by default is the scan giving up at the first unknown call
  • [1 SAFE] hooks/checks/lang/taint.js the reverse of the database gate → const q = base + req.query.id; then client.query(q); in a file holding no database vocabulary reports nothing at all
  • [1 SAFE] hooks/checks/lang/taint.js a parameter arriving already tainted is deliberately not followed → function f(q) { db.query(q); } is silent. Accepted: reporting it would fire on every data-access helper ever written
  • [5 FAST] hooks/checks/scan.js slices are balanced by file count, not by bytes → one slice holding the tree's large files finishes long after the others, which is why eight workers measure 2.2–2.5× rather than 8×
  • [1 SAFE] hooks/checks/lang/ts.js safe/xss-sink fires on the assignment target, not the value → el.innerHTML = render(x); is reported however render is written, because only a callee named as an escaper discharges it
  • [1 SAFE] hooks/checks/universal.js safe/redaction-marker only fires where a value belongs → the prose false positive is gone, and with it a marker in a Markdown table cell, which is a position the rule cannot read as a value
  • [1 SAFE] hooks/checks/deps.js safe/manifest-not-locked covers npm, go and cargo and no more → python, dotnet, maven and gradle manifests get safe/missing-lockfile and nothing else, and an unreadable manifest is reported under this same id rather than one of its own
  • [2 TRUE] hooks/checks/lang/py.js true/missing-timeout reads one line at a time → a multi-line call, a reqwest or HttpClient builder chain and an unbound receiver are each silent, and the dotnet pack has no timeout rule at all
  • [3 OBVIOUS] hooks/checks/shape.js a parameter list on a very long line has no ceiling → a 1,000-parameter single-line signature is measured and reported, because obvious/too-many-params is not span-derived and the 4 KB line guard does not cover it
  • [3 OBVIOUS] hooks/checks/toml.js a scalar and a table of the same name load as the table, silently → every other construct the parser cannot read exactly is warned about on stderr with file and line; this one is not
  • [3 OBVIOUS] hooks/procoder-check.js in-session findings are narrowed to the edited region and truncated to five → run procoder check on the file for the whole-file picture. Accepted: it buys an in-session notice that fits in a turn

None of those are hypothetical, and none of them are the whole list. Each was produced by running the tool on a throwaway file at 0.2.0.

Those fifteen lines are a pointer, not a second copy: every one of them is restated from docs/known-limitations.md, which is the only place a limitation is recorded, measured and dated. This page is a twin by rung 4's definition. What went from this page in this pass, every row struck because it was fixed and re-verified fixed: rungs 5 and 6 having no engine at all; PARALLEL_MIN_FILES counting files where the crossover is work; safe/redaction-marker reporting every sentence that explains redaction, and missing the lower-case, angle-bracket and unterminated spellings; safe/manifest-not-locked being npm-only, blaming peerDependencies, and skipping optionalDependencies, workspace packages and transitive-only direct dependencies; true/missing-timeout covering two packs and firing on **kwargs; the baseline nothing ever pruned; and the MCP server's silent five-finding truncation. If the two pages ever disagree, the markdown is right and this one is stale.

The engine covers the smaller half

The most important limitation is structural rather than a bug. procoder is two things, and only one of them is deterministic.

Where a finding can come from

The check engine is regex and counters over six languages. It runs after every file write and from the CLI, it is reproducible, and it is what CI gates on. It catches an interpolated query, a swallowed error, an over-long function, an unexplained suppression — 47 rule ids, across all six rungs.

The doctrine is text the agent reads. It catches the things no regex can: an authorization decision made from a value the caller supplied, a missing edge case, a name that lies, a replaced path nobody deleted. It is not reproducible, and it is not a gate CI can run.

For rungs 5 and 6 the overlap is three rules wide: fast/query-in-loop, fast/blocking-in-async and meant/unimplemented-stub. Everything else those two rungs ask is doctrine — a nested scan whose cost depends on a size no single file states, a rename nobody asked for, a feature quietly dropped. What was built for them and deliberately deleted, on evidence, is on the full list. A worked instance of the split — the same file, one half caught by the engine and the other only by the doctrine — is on the six rungs.

What the self-scan proves, and what it does not

tests/dogfood.test.js derives its file list from git ls-files, so every tracked file is in the gate the day it lands, this page and its stylesheet included. Running the tool over this repository today, node bin/procoder.js check . reports 0 findings over 212 tracked files and exits 0, having skipped 18 of them and said so on stderr for every one. The accounting of those 18 — and why each one is still the right call — is on Why it works this way, because a deliberate exclusion that reports itself on every run is a decision rather than a weakness. So 194 files are actually read: the number the README publishes, and the one tests/dogfood.test.js asserts against the scan's own output so it cannot drift.

What that does not prove: the scan is only as strong as the engine, and the engine is the smaller half. A clean self-scan means procoder finds nothing wrong with procoder — which is exactly the claim a heuristic tool is worst placed to make about itself. It is evidence that the tool is not exempting itself, not evidence that the code is correct.

It also does not exercise the worker pool. The scan forks on measured sequential milliseconds rather than on a file count — the threshold is PARALLEL_MIN_WORK_MS, 900 ms, and the measurement comes from scanning a strided sample of the run's own files for real. This repository measures 737 ms sequentially, so procoder check . over procoder itself never forks. Tests reach the pool through a forceParallel option that exists for that reason and no other.

Two of the ignored paths carry a gap rather than a decision. docs/superpowers/ is ignored because procoder still cannot tell a document quoting a violation from a file committing one at the scale of a 1,500-line planning document — 56 findings under --no-ignore, every one of them meta-text. And no staleness report of any kind reaches --format json or sarif: all three instruments are verify output, --format is refused off check, so a dashboard-only pipeline has to run a second, text-mode verify to learn that a directory has been quietly un-gated.

The full list

docs/known-limitations.md is the authoritative document. Every entry in it was verified against the source cited next to it, or by running the tool, and it carries its own note saying when that verification was done. Entries that were fixed are deleted rather than kept as false modesty — a document that overstates weakness is as untrustworthy as one that hides it. Its companion, Why it works this way, carries the decisions that cost nothing and used to be filed there as though they did.

This page does not restate it. Here is the map:
