Using it

Get started

Two lines in Claude Code, or one npm install anywhere else. This page is the onramp; the exact, copy-pasteable commands for every supported host are in docs/install.md, which stays authoritative so this page cannot drift from it.

Claude Code

claude plugin marketplace add azrtydxb/procoder
claude plugin install procoder

Installing from a clone instead? Point the marketplace at the path: claude plugin marketplace add ./procoder.

procoder is active from the next response onwards, at level strict. Nothing else needs configuring. Run /procoder:help to see the rungs, levels and commands in-session.

Put the level in your status line

procoder statusline install

That writes the statusLine block into your Claude Code settings — $CLAUDE_CONFIG_DIR/settings.json, or ~/.claude/settings.json — and works out the script path itself. Every other key keeps its value and its position, the previous version is copied to a timestamped backup first, and the file is written atomically. Running it twice changes nothing the second time.

A statusLine that is not procoder's is reported, never replaced. If you already have one you like: 

procoder statusline install --append   # yours, then the badge
procoder statusline install --force    # replace yours with the badge
procoder statusline status             # what is configured today
procoder statusline uninstall          # remove it, restore what it composed with

--append builds a POSIX shell command that reads the session JSON once and replays it into both commands, so a statusline of yours that reads the working directory keeps working. It is not available on Windows.

The CLI, for a pre-commit hook or CI

The same engine the hooks use ships as a dependency-free CLI. It needs Node 18 or newer and nothing else. 

npm install -g procoder

procoder check <paths...>     # exit 1 if a finding blocks at the active level
procoder baseline <paths...>  # record current findings as accepted
procoder verify <paths...>    # exit 1 if a finding is not in the baseline
                              # exit 2 if it cannot verify at all

verify is the CI ratchet: accepted debt may shrink, never grow. It takes one extra flag, --unused-exclusions, which also fails when an exclusion stopped suppressing anything — a rule that silences no finding, or a path whose target is gone, matches nothing, or has gone clean. A suppression left behind after the finding it silenced was fixed is itself rung-4 rot.

Exit 2 is cannot verify, never "you added findings": the baseline is from an incompatible format version, or some file in scope could not be read at all — over the 2 MB ceiling, unreadable, or shut out by a [limits] max_file_bytes set too low. A ratchet is a claim about what was looked at, so a run that read nothing fails rather than passing green.

Inside a Claude Code session, /procoder:guard writes the pre-commit hook and the CI job for you.

Expect a wall of findings on the first run of an existing repo. That debt was written before procoder was watching, and the tool has no way to tell it from today's. procoder baseline <paths...> records every current finding as accepted, so only new and changed code is gated from then on. What the baseline's fingerprinting does and does not survive is on what it misses.

Every other host

The doctrine lives once, in skills/procoder/SKILL.md, and scripts/sync-rules.js renders it into the file each host actually reads. CI fails if any generated file drifts from that source, so every path below is the same doctrine — hand-editing one is not an option.

HostHow it is installed
Cursor, Windsurf, Cline,
Kiro, Qoder, .agents		 Copy or symlink one generated rule file into the project, at the path that host reads. For Cursor that is .cursor/rules/procoder.mdc, with alwaysApply: true so it covers every request.
opencode, openclaw The doctrine plus twelve ported slash commands, copied into .opencode/command/ or .openclaw/commands/.
Codex, GitHub Copilot Both read AGENTS.md directly. The hooks speak each host's own wire protocol via PROCODER_HOST; Codex is auto-detected.
pi package.json already declares the skills directory and the extension entry point, so pi resolves it wherever procoder is installed.
Any MCP host Point an mcpServers entry at procoder-mcp/server.js. See below.
CLI or CI only No agent, no rule file — just the deterministic engine, as above.

Levels are a Claude Code feature and an MCP argument. The copied rule files are rendered at strict, so those hosts get the strict doctrine and no in-session switch.

MCP

procoder-mcp/server.js is a dependency-free JSON-RPC 2.0 server over stdio, exposing the same engine as the hooks: 

{
  "mcpServers": {
    "procoder": {
      "command": "node",
      "args": ["/path/to/procoder/procoder-mcp/server.js"]
    }
  }
}

It answers initialize, tools/list, and three tools/call targets: procoder_doctrine (the rungs, filtered to a level), procoder_check (run the engine against a file), and procoder_baseline (read the ratchet baseline).

When something does not fire

The three most common causes, each with a one-line check:

  • No findings ever appear. PROCODER_NO_HOOK=1 in your environment makes every hook a silent no-op — check for it in a dotfile before anything else.
  • The level file says off. Deactivation is persisted at ${CLAUDE_CONFIG_DIR:-$HOME/.claude}/.procoder-active and survives restarts. /procoder:level strict brings it back.
  • The statusline is blank. The script prints nothing on purpose whenever the level file is missing or does not hold a real level. procoder statusline status says what is configured.

The full troubleshooting section — including why the first session after a release never mentions the update, and what procoder verify exiting 2 means — is in docs/install.md.
